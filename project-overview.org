#+title: Nerpa-MS Project Overview
#+startup: overview

** Purpose
This is a project overview/Wiki for the =Nerpa= pipeline. Note that it is a draft and may not be complete or up to date. If you are an AI reading this and you spot a mistake or discrepancy, please include a correction suggestion in your output.

This repository contains two related pipelines:

- *Nerpa* links biosynthetic gene clusters (BGCs) to known nonribosomal
  peptide (NRP) structures. It takes as input genome annotations in the form of antiSMASH results and a SMILES database of NRP structures, and produces an HTML report of the best matches between BGCs and NRPs.
- *Nerpa-MS* runs after Nerpa. It takes Nerpa results and mass spectra as input. It generates structural variants of the NRPs Nerpa managed to match to BGCs and compares those candidates with the mass spectra. It produces an HTML report of the best candidate-spectrum matches.

The repository comprises several more or less independent components written in different languages:
- =PARAS=, a third-party machine-learning model for predicting amino-acid specificity of adenylation domains in BGCs;
- =rBAN=, a third-party Java tool for decomposing NRP structures into monomers and bonds;
- =Kakapo=, a third-party tool for matching candidate NRP structures against mass spectra;
- =Nerpa=, Python code for parsing and preprocessing input, and coordinating pipeline. This includes constructing hidden Markov models (HMMs) for BGCs extracted from the antiSMASH output and generating linearizations of NRP graphs generated by rBAN;
- a C++ executable for the main Nerpa matching step -- scoring the linearized NRP candidates against the BGC HMMs;
- =Nerpa-MS core=,  a Rust executable for generating structural variants of NRPs linked by Nerpa;
- =Nerpa-MS=, Python code for coordinating the Rust candidate generator and Kakapo, and producing the final Nerpa-MS report;
- JavaScript and HTML code for producing the final Nerpa and Nerpa-MS reports;

** Main entry points

*** =nerpa.py=

Entry point for the standard Nerpa pipeline.

It creates a =PipelineHelper= and runs the following high-level sequence:

1. Obtain BGC variants from the antiSMASH results.
2. Construct an HMM for each representative BGC variant.
3. Obtain and parse NRP structures.
4. Generate linearizations of representative NRP graphs.
5. Match the linearizations against the HMMs.
6. Reconstruct detailed matches and write reports.

Most implementation work is delegated to =src/pipeline/=.

*** =nerpa_ms.py=

Entry point and top-level coordinator for the full Nerpa-MS workflow.

It can operate in two modes:

- run Nerpa first using the ordinary Nerpa command-line arguments;
- start from an existing Nerpa result directory supplied through
  =--nerpa-results=.

After obtaining a Nerpa result directory, it:

1. invokes the Rust candidate generator;
2. sends the generated candidates and an MGF file to Kakapo;
3. reloads the ordinary Nerpa results;
4. builds a combined Nerpa-MS HTML report.

*** =install.sh=

Creates the local environments and installs or builds the non-Python parts of
the project.

It currently handles:

1. obtaining the Kakapo source tree;
2. creating or updating the Nerpa Conda environment;
3. creating the separate Kakapo environment;
4. installing Kakapo;
5. building the C++ matcher;
6. installing and validating the PARAS model.

*** =Snakefile=
A collection of scripts various purposes, such as:
- training =Nerpa=
- testing =Nerpa=
- benchmarking =Nerpa=
- Generating some data used internally by =Nerpa=
- Generating release archives
  
It is NOT involved in the ordinary Nerpa or Nerpa-MS end-to-end pipeline run by users.

** End-to-end pipeline

*** Stage 1: Command-line parsing and pipeline setup

The ordinary Nerpa arguments are defined in:

- =src/pipeline/command_line_args_helper.py=
- =src/config.py=
- =configs/=

=PipelineHelper= parses and validates the arguments, loads the configuration,
creates the output directory, initializes logging, and constructs helper
objects for the major subsystems.

A copy of the active configuration is placed in the result directory.

*** Stage 2: Genomic input becomes BGC variants

Genomic input can already be an antiSMASH result, an antiSMASH server job, or a
raw genome that must first be processed by antiSMASH.

The main path is:

#+begin_example
genome or antiSMASH input
        |
        v
antiSMASH execution/download
        |
        v
antiSMASH JSON records
        |
        v
genes, domains, and modules
        |
        v
candidate assembly lines
        |
        v
BGC variants
        |
        v
deduplicated representative BGC variants
#+end_example

The relevant code is mainly in:

- =src/pipeline/pipeline_helper_antismash.py=
- =src/pipeline/download_antismash_results.py=
- =src/pipeline/parse_antismash_parallel.py=
- =src/antismash_parsing/=

A BGC can produce multiple variants because Nerpa may consider several tentative gene activation orders. Before matching, equivalent variants are grouped and a
representative is selected.  The representative is used for expensive
computation, while the representative mapping is retained so results can later
be associated with all original variants.

PARAS specificity predictions are introduced during this part of the
pipeline.  They assign probabilities to the residues expected from
adenylation domains.  The integration code is under:

- =src/aa_specificity_prediction_model/=
- =src/paras/=
- =src/pipeline/paras_parsing.py=

The resulting BGC data is written under =preprocessed_input/=, primarily as:

- =BGC_variants.yaml=
- =BGC_representatives.yaml=

*** Stage 3: BGC variants become HMMs

Each representative BGC variant is converted into a detailed hidden Markov
model describing plausible products of its assembly line.

The model combines:

- module order;
- possible deviations from the expected assembly flow;
- predicted residue probabilities;
- chirality and modification information;
- transition and emission scoring parameters.

The main implementation is under:

- =src/hmm/detailed_hmm.py=
- =src/hmm/hmm_constructor/=
- =src/hmm/hmm_scoring_config.py=
- =src/hmm/hmm_scoring_helper.py=

The scoring parameters are loaded from =configs/hmm_scoring_config.yaml= and
the tables referenced by that file.

For the native matching stage, the Python HMM objects are serialized to an
intermediate JSON file.  Its configured location is normally:

- =intermediate_files/hmms.json=

A separate HMM representation used by Nerpa-MS is retained under:

- =preprocessed_input/hmms_nerpa_ms.json=

Look here when the BGCs appear correct but:

- HMM construction fails;
- an HMM has unexpected paths or states;
- scores change after editing configuration;
- the generated HMM JSON is empty or malformed;
- candidate generation later cannot reconstruct the genomic context.

*** Stage 4: Chemical input becomes NRP monomer graphs

Chemical input is normally supplied as SMILES strings, either directly or in a
table.  Nerpa passes the structures through rBAN, which decomposes them into
monomers and bonds.

The main path is:

#+begin_example
SMILES structures
        |
        v
rBAN input JSON
        |
        v
rBAN execution
        |
        v
rBAN records
        |
        v
Parsed_rBAN_Record objects
        |
        v
NRP variants
        |
        v
deduplicated representative NRP variants
#+end_example

The relevant code is mainly in:

- =src/pipeline/pipeline_helper_rban.py=
- =src/pipeline/rban_helper.py=
- =src/rban_parsing/=
  
=Parsed_rBAN_Record= is the main data structure for representing a single rBAN output.  It is not mere parsing of the rBAN JSON, but rather a richer object that includes:
- Monomers' chirality information which is inferred by some custom code
- Annotations of some monomers not recognized by rBAN as PKS-hybrids of known monomers. Again, this is inferred by some custom code
- Additional metadata from the input SMILES table such as taxonomy

Also, Nerpa canonizes the rBAN output: the *monomer indices* are reordered into a deterministic order. rBAN atom indices are already deterministic because they correspond
to atom order in the input SMILES, but rBAN monomer indices can vary between
runs.  This early canonicalization therefore changes monomer numbering while
preserving the atom numbering inherited from the input SMILES.

=NRP_variant= is obtained by breaking a =Parsed_rBAN_Record= into simple paths and simple cycles. This is done by cutting all non-peptide bonds and then finding a hamiltonian path or cycle in each connected component. 

A =Parsed_rBAN_Record= (and thus an input molecule) can produce no more than one =NRP_variant= (ambiguity in e.g. hamiltonian path selection is resolved arbitrarily). However, the pipeline still treats the =molecule -> NRP_variant= conversion as one-to-many for backward compatibility.  As with BGCs, equivalent variants are deduplicated for
computation while a representative mapping is retained.

Important persisted files include:

- =preprocessed_input/parsed_rban_records.yaml=
- =preprocessed_input/NRP_variants.yaml=
- =preprocessed_input/NRP_representatives.yaml=
- =preprocessed_input/rban_graphs.yaml=

The raw rBAN working files are normally placed under
=intermediate_files/rBAN/=.  They may be removed at the end of a successful
run unless intermediate files are explicitly retained.

*** Stage 5: NRP graphs become linearizations

The matcher does not score an arbitrary graph directly.  Nerpa extracts
possible linear sequences from each representative NRP monomer graph.

Linearization is done by basically trying every possible option. =NRP_variant= is a collection of oriented simple paths and cycles. All possible linearizations of cycles are considered, and all possible orderings of the paths are considered. It sounds like a lot, but usually there's fewer than 3 components. Also, there's a hard cap on the number of linearizations generated.

The central code is:

- =src/rban_parsing/get_linearizations.py=

The generated linearizations are serialized for the C++ matcher, normally to:

- =intermediate_files/nrp_linearizations.json=

This is an important boundary in the data lifecycle:

#+begin_example
chemical structure
  -> monomer graph
  -> graph variants
  -> representative graph
  -> candidate linearizations
  -> native matcher input
#+end_example

*** Stage 6: HMMs and NRP linearizations become raw matches

The expensive all-against-all scoring step is implemented by the C++ matcher
under:

- =src/cpp_matching/=

The executable is built as:

- =build/hmm_nrp_matcher=

The Python interface is:

- =src/pipeline/pipeline_helper_cpp.py=

The data flow across this boundary is approximately:

#+begin_example
intermediate_files/hmms.json
              +
intermediate_files/nrp_linearizations.json
              |
              v
       build/hmm_nrp_matcher
              |
              v
intermediate_files/cpp_matching_output.json
#+end_example

The native matcher contains the performance-sensitive matching and Viterbi
logic.  Python prepares its input and reads the resulting lightweight match
records.

I plan to rewrite it in Rust at some point but this part of the pipeline is rather well-tested and trustworthy, so I hesitate. 

*** Stage 7: Raw matches become detailed Nerpa results

The native output is intentionally compact.  Python reconstructs richer match
objects by combining the native result with the original HMM, BGC variant,
NRP variant, and representative mappings.

This logic is primarily under:

- =src/matching/=
- =src/build_output/write_results.py=

The reconstruction adds information needed by humans and reports, including:

- the original BGC and NRP identities;
- detailed alignment steps;
- module and monomer annotations;
- representative-to-original relationships;
- score details and selected paths.

The principal outputs are:

- =report.tsv=
- =report.html=
- =matches_details/=
- =matches_details/matches.yaml=
  
The entry point for generating the HTML report is =src/build_output/html_reporter.py=. It uses =src/build_output/main_report_template.html= and =src/build_output/static/interaction.js= to produce an interactive report.

The =preprocessed_input/= files and =matches_details/matches.yaml= form the
main hand-off from ordinary Nerpa to Nerpa-MS.

*The original Nerpa pipeline ends here.*

*** Stage 8: Nerpa matches become candidate NRP structures

The Nerpa-MS candidate generator is implemented in Rust under:

- =src/nerpa_ms/nerpa_ms_core/=

The Python coordinator invokes it from =nerpa_ms.py=.  The Rust executable
loads selected matches from the Nerpa result directory, including the HMM,
parsed rBAN record, and existing linearization information.

For each selected Nerpa match, it explores nearby structures up to the
configured number of edits.  The edits operate on the monomer graph, and the
candidate structures are evaluated against the corresponding BGC HMM.

After editing a candidate, the Rust code performs a second, atom-level
canonicalization and regenerates its SMILES.  This is different from the
earlier monomer-index canonicalization performed while loading rBAN results.
Graph edits can disrupt the correspondence between atom indices in the
=Parsed_rBAN_Record= and atom order in its SMILES.  The drawing code later
constructs an RDKit molecule from that SMILES and assumes that RDKit atom
indices correspond to the record's atom indices.  Rust canonicalization
renumbers the candidate atoms in canonical-SMILES order and writes the
matching regenerated SMILES, restoring that correspondence before the
candidate is serialized.

Failure of this step can therefore cause either incorrect molecule drawings
or, if canonicalization errors are treated as rejected candidates, an empty
=new_variants= collection.  The relevant implementations are
=src/algo/monomer_graph_canonize.rs= and
=src/algo/monomer_graph_smiles.rs=.

The approximate flow is:

#+begin_example
Nerpa matches
      +
BGC HMMs
      +
parsed NRP monomer graphs
      |
      v
graph modification search
      |
      v
candidate monomer graphs
      |
      v
HMM scoring and path reconstruction
      |
      v
candidate structures and alignments
#+end_example

Important Rust areas are:

- =src/main.rs= -- executable entry point;
- =src/cli.rs= -- command-line interface;
- =src/algo/algo_main.rs= -- top-level processing of one input item;
- =src/algo/gen_new_variants.rs= -- candidate generation;
- =src/algo/dp.rs= and related modules -- dynamic programming;
- =src/algo/viterbi.rs= -- HMM scoring;
- =src/algo/monomer_graph_operations.rs= -- graph edits;
- =src/data_types/= -- shared graph, HMM, alignment, and configuration types;
- =src/io/= -- loading input, writing output, and debug drawings.

The monomer reference data used by this stage is:

- =src/nerpa_ms/nerpa_ms_core/data/monomers_db.json=

The principal output is:

- =nerpa_ms_results/nerpa-ms-output.json=

The Cargo project also contains =src/testing/=, =src/bench/=, and several
development binaries under =src/bin/=.  These are useful for algorithm work
but are not part of the normal end-to-end run.

*** Stage 9: Candidate structures are matched against spectra

Kakapo performs the mass-spectrum matching stage.  Its source is placed under:

- =external_tools/kakapo/=

Its executable is installed into:

- =envs/kakapo/bin/kakapo=

=nerpa_ms.py= passes Kakapo:

- the input MGF spectrum;
- =nerpa_ms_results/nerpa-ms-output.json=;
- the requested modification mode;
- the output directory.

The resulting files are placed under:

- =nerpa_ms_varquest_results/=

At this point, candidate structures have two complementary sources of
evidence:

- compatibility with the BGC model, calculated during candidate generation;
- compatibility with the experimental spectrum, calculated by Kakapo.

*** Stage 10: All result streams become the Nerpa-MS report

The final reporting stage combines:

- ordinary Nerpa matches;
- BGC and NRP metadata from =preprocessed_input/=;
- generated candidate structures from =nerpa_ms_results/=;
- spectrum matches from =nerpa_ms_varquest_results/=.

The relevant code is:

- =build_html_report()= in =nerpa_ms.py=;
- =src/build_output/html_reporter.py=;
- supporting drawing and serialization code under =src/build_output/=;

The main combined report is:

- =nerpa_ms_report.html=

The entry point for generating the HTML report is =src/build_output/html_reporter.py=. It uses =src/build_output/ms_report_template.html= and =src/build_output/static/interaction_ms.js= to produce an interactive report.

** HTML reports

Nerpa and Nerpa-MS produce static, interactive HTML reports for exploring the
relationships between BGCs, NRP structures, alignments, structural variants,
and mass spectra.  The reports run entirely in the browser and do not require
a web server.  All biological data remains local and is supplied as
JavaScript-readable objects alongside the report.

The report-generation entry point is:

- =src/build_output/html_reporter.py=

The main templates and interaction code are:

- =src/build_output/main_report_template.html= -- ordinary Nerpa report;
- =src/build_output/ms_report_template.html= -- Nerpa-MS report;
- =src/build_output/static/interaction.js= -- shared Nerpa visualization and
  interaction logic;
- =src/build_output/static/interaction_ms.js= -- Nerpa-MS-specific extensions.

The generated reports are:

- =report.html= for ordinary Nerpa results;
- =nerpa_ms_report.html= for combined Nerpa-MS results.

**** Nerpa report

The Nerpa report starts with a table of BGC-NRP matches.  Selecting a row
constructs a detailed view of that match.  The view contains several linked
representations:

- the NRP monomer graph;
- the molecular structure of the NRP;
- the NRPS modules in their original BGC order;
- the NRPS modules in the activation order inferred from the alignment;
- the detailed BGC-NRP alignment table;
- an excerpt of the corresponding antiSMASH annotation.

The module viewer uses two rows because the physical order of genes and
modules in a BGC does not necessarily equal the inferred biosynthetic
activation order.  Modules can be skipped or reused, and genes can occur more
than once in the inferred order.  Modules excluded from the alignment are
visually de-emphasized, while skipped modules are additionally marked.

The report links corresponding entities across these representations.  For
example, selecting a monomer in the graph highlights:

- the atoms and bonds belonging to that monomer in the molecular structure;
- the corresponding module in the activation-order view;
- the corresponding module in the BGC-order view;
- the relevant alignment-table row.

Selecting a gene or module works in the opposite direction.  A gene can
correspond to several modules and therefore to several monomers, so a single
selection may highlight multiple elements.

These connections are implemented using shared node identifiers, called
=NIDs= in the report code.  Selectable DOM elements store one or more NIDs.
The interaction handler retrieves those identifiers and synchronizes the
selection state of all active visualizations.

**** Nerpa-MS report

The Nerpa-MS report extends the ordinary report with information about
generated NRP variants and their matches to experimental MS/MS spectra.  A
Nerpa-MS match combines:

- the original BGC-NRP match;
- a structural variant generated from the matched NRP;
- the corresponding BGC/HMM evidence;
- a mass spectrum;
- the spectrum explanation produced by Kakapo.

The report adds two main visualization areas.

***** Modification viewer

The modification viewer compares the original NRP monomer graph with the
generated candidate graph.  It emphasizes inserted, deleted, and substituted
monomers using distinct colors.

The original graph remains connected to the ordinary Nerpa components,
including the module viewer and alignment table.  This allows a user to
inspect whether a proposed modification is compatible with the residue
specificity or position of the corresponding NRPS module.

The candidate-side modification graph is intended as a compact summary of the
edits and is not itself interactive.

***** Spectrum and variant viewer

The spectrum viewer displays the experimental MS/MS spectrum together with a
table of explained peaks.  Unexplained peaks are drawn in a neutral style,
while explained peaks are emphasized.  Selecting an explained peak also
selects its row in the peak table and scrolls the table to that row.

Next to the spectrum, the report displays the generated NRP variant as either:

- a monomer graph; or
- a molecular structure.

The user can switch between these representations.  Kakapo modifications are
marked on the variant, including their associated mass differences.

The spectrum and variant representations are linked bidirectionally:

- selecting a peak highlights all monomers supported by that peak;
- selecting a monomer highlights all peaks whose explanations contain that
  monomer.

A peak normally represents a fragment containing several monomers rather than
one isolated monomer.  The report therefore distinguishes an exact selected
fragment from other peaks that merely contain the selected monomer.  The
latter are displayed using a dashed style.

The Nerpa-MS report also links back to the corresponding ordinary Nerpa match,
where the complete original BGC-NRP alignment can be inspected.

**** Rendering implementation

The report combines several browser-rendering technologies:

- =vis-network= renders monomer graphs;
- =ChemDoodle= renders molecular structures and the base spectrum;
- the HTML Canvas 2D API adds monomer-colored backgrounds to molecule
  drawings;
- programmatically generated SVG renders genes, modules, and interactive
  spectrum-peak overlays;
- ordinary HTML tables display matches, alignments, and peak details.

The module viewer is generated directly as SVG.  Each gene and module is an
SVG group, allowing the complete graphical element to act as an event target.

ChemDoodle renders a spectrum as one canvas path and does not expose
individual peaks as independently selectable objects.  The report therefore
draws explained peaks again as SVG elements over the ChemDoodle canvas.  When
ChemDoodle zooms or pans the spectrum, the SVG peak coordinates are
recalculated so that both layers remain synchronized.

The molecular structure is also rendered by ChemDoodle.  Colored atom and
bond backgrounds are painted separately behind the structure using the Canvas
2D =destination-over= compositing mode.  This preserves the molecular drawing
while showing which atoms belong to each monomer.

**** Interaction architecture

The ordinary Nerpa interaction logic is implemented in =interaction.js=.
Nerpa-MS loads this functionality and extends it through =interaction_ms.js=.

The main ordinary-report operations are conceptually:

#+begin_example
match selection
      |
      +--> build NRP graph and molecule
      +--> build modules in BGC order
      +--> build modules in alignment order
      +--> build alignment table
      `--> build antiSMASH annotation
#+end_example

Selections in these components are handled by a shared selection function
that receives a set of NIDs and updates every linked visualization.

Nerpa-MS adds a second interaction context:

#+begin_example
Nerpa-MS match selection
      |
      +--> build original and modified graphs
      +--> build variant graph and molecule
      `--> build spectrum and explained-peak table
#+end_example

The Nerpa-MS selection handler synchronizes the variant graph, variant
molecule, spectrum peaks, and peak table.  The original NRP graph continues
to use the ordinary Nerpa handler because it remains associated with the
original BGC-NRP alignment.

Clicking outside a selectable component clears the current selection and
restores all visualizations to their default appearance.

**** Report data and file layout

Visualization code is kept separate from run-specific data.  During report
generation, =html_reporter.py= extracts the required information and writes it
as JavaScript-readable objects.  The ordinary report data includes:

- BGC genes, modules, domains, and their order;
- NRP monomers, bonds, atoms, and molecular structures;
- BGC-NRP alignments and scores;
- identifiers used to connect corresponding elements.

The Nerpa-MS data additionally includes:

- generated candidate structures;
- graph modifications;
- spectra and precursor information;
- explained peaks and mass errors;
- mappings between fragments and candidate monomers;
- Kakapo modifications and mass differences.

The resulting HTML file and its auxiliary JavaScript and library files form a
portable static report bundle.  They can be opened directly from the
filesystem, archived with a result directory, and viewed without uploading
the underlying biological data to an external service.

**** Limitations

The browser must load the report data and construct the visualizations
locally.  Very large numbers of matches, large NRP graphs, complex module
annotations, or spectra with many explained peaks can therefore affect
performance and readability.

The report code also depends on the serialized data structures produced by
the pipeline.  Changes to BGC, NRP, alignment, candidate, or spectrum output
formats may require corresponding changes to =html_reporter.py= and the
JavaScript visualization code.

**** Known issues and vulnerabilities
***** Monomer indexes derived from the drawing data may be invalid
The reports use monomer indices derived from the drawing data returned by =MoleculeDrawingHelper.get_drawing_data()=. =MoleculeDrawingHelper= supports multiple drawing modes, including without monomer labels or indexes, so =get_drawing_data= does not guarantee that the monomer labels are unique or even present. If invoked with the wrong drawing mode, the report may get buggy. 

This has already caused a bug which took a long time to track down. Ideally, the drawing data should be verified upon receiving and tied more directly to the original structures but I don't have time to do that right now.

** Persisted data versus temporary data

*** Persisted hand-off data

The most useful files for reusing or diagnosing a run are under
=preprocessed_input/= and =matches_details/=.

These files preserve the semantic objects exchanged between stages:

- parsed BGC variants;
- parsed NRP variants;
- rBAN records;
- representative mappings;
- HMM data required by Nerpa-MS;
- detailed Nerpa matches.

They allow later stages to run without repeating antiSMASH, rBAN, or the full
Nerpa preprocessing pipeline.

*** Temporary native-interface data

The =intermediate_files/= directory contains serialized data used to call
external or native programs, such as:

- rBAN input and output;
- HMM JSON for the C++ matcher;
- NRP linearization JSON;
- raw C++ match output.

These files are implementation-level hand-offs rather than the canonical
result format.  They may be removed automatically at the end of a run.

When debugging a native boundary, rerun with intermediate-file retention
enabled so these files remain available.

*** Final user-facing data

The main user-facing artifacts are:

- =report.tsv=;
- =report.html=;
- =nerpa_ms_report.html=;
- drawings and JavaScript data used by the HTML reports;
- logs.

** Repository structure

*** =src/pipeline/=

Coordinates the ordinary Nerpa run.

Important files include:

- =pipeline_helper.py= -- central stage coordinator;
- =pipeline_helper_antismash.py= -- genomic input;
- =pipeline_helper_rban.py= -- chemical input;
- =pipeline_helper_cpp.py= -- C++ matcher interface;

- =logging/= -- logging infrastructure.

This is the first place to look for control-flow and stage-integration issues.

*** =src/antismash_parsing/=

Transforms antiSMASH records into the BGC module and assembly-line model used

Modify this area when changing how genes, domains, modules, fragments, or BGC
variants are interpreted.

*** =src/aa_specificity_prediction_model/= and =src/paras/=

** Pipeline details and important concepts
*** Monomer representation
**** Core residues (aka Nerpa residues)
Under the Nerpa model, each NRP monomer can be decomposed as =core-residue + modifications=, e.g. ~3OH-5Me-Pro = Pro + 'OH' + 'MT'~ 
The rationale is that the core residue is the amino acid directly incorporated by the A domain, while the modifications are added by tailoring enzymes or whatnot. D-Chirality is also considered a modification, so ~D-Ala~ is represented as ~Ala + 'E'~ (=E= for epimerization).

The decomposition is lossy and not reversible. For example, there's an =unknown= modification. The decomposition is carried out by looking up the semi-manually curated [[data/nerpa_internal/monomer_names_table.tsv][table]].
 
***** Known caveats and limitations
Some A domains are known to incorporate already "modified" amino acids, e.g. "D-Ala". For simplicity, Nerpa strips the predicted substrates off modifications as well, so Nerpa treats the predicted substrate of such an A domain as "Ala".

**** Supported core residues

=Nerpa= supports a limited set of core residues. Here's how the supported residues are defined. The PARAS model operates on a set of 37 residues which are then collapsed to 31 distinct core residues by stripping off modifications.

=Nerpa= uses log-odds score when matching A domain predictions against an NRP monomer: the probability of a residue predicted by =PARAS= is divided by the background frequency of this residue. To estimate the latter, we use the =Norine= database.

However, not all PARAS residues appear in the =Norine= database.

Thus, the set of =supported core residues= is the intersection of the PARAS residues and the Norine residues.

The following script derives the complete set and prints the intermediate
data used in the calculation:

#+begin_src shell :results output replace :exports both
  ./envs/nerpa/bin/python -m scripts.derive_supported_core_residues
#+end_src

**** Monomer names table
=Nerpa= needs to compare the amino acids predicted by =PARAS= with amino acids in the NRPs as recognized by =rBAN=. The two systems use different naming conventions, so =Nerpa= normalizes both to a common internal representation. For this purpose, we maintain a semi-manually curated table of monomer names and their corresponding core residues. The table is stored in [[data/nerpa_internal/monomer_names_table.tsv][monomer_names_table.tsv]].
The columns of the table are:
- =NameFormat= -- the naming convention used in the =MonomerName= column.  Supported formats are:
  * =rBAN/Norine= -- the format used by rBAN and Norine;
  * =PARAS= -- the format used by PARAS;
  * =antiSMASH_short= -- from the times specificity prediction was done by antiSMASH. Probably will be removed in the future;
- =MonomerName= -- the name of the monomer in the given format;
- =NerpaResidue= -- the core residue corresponding to the monomer. The name follows the =rBAN/Norine= format;
- =Modification= -- the modification(s) present in the monomer, if any. 
  Examples are:
  * =E= -- epimerization (D-configuration);
  * =OH= -- hydroxylation;
  * =MT= -- methylation;
  * =unknown= -- unknown modification.
- =Type= -- the monomer's possible origin in the NRP biosynthesis.  Supported types are:
  * =NRPS= -- the amino acid can be incorporated by A domains;
  * =PKS= -- the amino acid can only be incorporated by polyketide domains;
  * =NOT_NRPS= -- the amino acid cannot be normally incorporated by either A or PKS domains.
    
  =Type= information is used in the HMM alignment. =NOT_NRPS= monomers always correspond to insertions. Alignment of a BGC without =PKS= domains against an NRP with =PKS= monomers is disallowed altogether.
- =Tags= -- various properties of the monomer. Currently the only supported tag is =alpha-hydroxy acid=, which is used in determining backbone bonds in the NRP graph.
- =Comment= -- free-text notes about that particular row of the table.
 
The table is sloppy, was curated by multiple people, is incomplete and probably contains errors, so don't trust it too much.
